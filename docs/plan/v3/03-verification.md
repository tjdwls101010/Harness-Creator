# 검증 — claim A/B 프로토콜과 L5 도그푸딩

> `GuardrailTests`의 토큰 앵커는 *삭제*를 잡고 *희석*을 못 잡는다. v2 압축에서 손실 4건이 났고, 그중 하나가 **검사 문장 자체**였다 — 원칙만 남기고 검사를 자른, 이 스킬이 경고하는 rail/principle 역전 그대로. 앵커만으로 v3를 하면 재발이 거의 확실하다.

## 1. 왜 claim 추출인가

희석은 diff에 안 보인다. 문장이 사라진 건 읽히지만, 문장이 **약해진** 건 안 읽힌다 — "silently"가 빠진 문장, 조건절이 잘린 규칙, 예외가 없어진 숫자는 diff에서 정상적인 축약처럼 보인다.

claim 추출은 이걸 기계적 문제로 바꾼다. **원본에서 원자적 주장 집합을 뽑고, 원본을 못 본 독립 에이전트가 압축본에서 같은 방식으로 뽑고, 차집합을 본다.** 압축본 추출자가 원본을 못 봤다는 게 핵심이다 — 원본을 본 리뷰어는 "원본에 있었으니 이해된다"는 편향으로 손실을 못 본다.

## 2. 프로토콜

### 2.1 claim의 정의

**원자적 주장 = 사라지면 이 파일의 독자가 무언가를 틀리게 만드는, 하나의 반증 가능한 진술.**

7가지 kind로 분류한다. 분류 자체가 do-not-cut(`02-compression.md` §2.3의 N1–N6)과 맞물린다.

| kind | 정의 | 대응 do-not-cut |
|---|---|---|
| `mechanism` | Claude Code가 어떻게 동작하는지에 대한 사실 (필드명, 기본값, 버전 플로어, 정확한 값, 무엇이 언제 로드되는지) | N5 |
| `decision-rule` | 어떤 조건에서 무엇을 고르라는 진술 | — |
| `test` | 독자가 적용할 검사나 질문 | **N1** |
| `counter-case` | 규칙이 적용되지 *않는* 사례 | **N3** |
| `silent-failure` | 어떤 실패가 아무 신호도 내지 않는다는 진술 | **N4** |
| `number-with-exception` | 임계값 + 성립하지 않는 경우 | **N2** |
| `rationale` | 규칙에 대해 명시된 이유 | N6 |

**입도 규칙:** 200단어 문단은 보통 원자적 주장 3~8개를 담는다. 두 주장을 한 항목으로 병합하지 않는다. 연결 산문·재진술·설득 문장은 claim이 아니다.

### 2.2 4단계

```
① 원본 추출 ×2   (독립 에이전트 2개, 원본 파일)
     └ 두 결과의 합집합이 기준선. 근접 중복은 하나로 센다.
     └ 두 결과가 크게 다르면 추출 프로토콜 자체가 불안정하다는 신호다.
② 압축         (판별식 프롬프트로 압축, 결과를 스크래치패드에 씀)
③ 블라인드 추출  (원본을 못 본 에이전트가 압축본에서만 추출)
④ 판정         (①의 합집합 vs ③을 대조 → 손실/약화 보고)
```

**④ 전에 kind 분포부터 본다 — 공짜 신호다.** 파일럿에서 이게 실제로 후보 손실을 잡아냈다(§3.3). 판정 에이전트를 돌리기 *전에* 이 표를 먼저 만든다.

```
kind별 개수를 orig(합집합) vs blind로 나란히 놓는다.
표 변환은 주장을 이산화하므로 총량과 대부분의 kind는 오르는 게 정상이다.
어떤 kind가 "떨어지면" 그게 후보 손실이고, 판정 에이전트에게 그 kind를 우선 보라고 지시한다.
```

**④의 판정 기준 — 엄격하게:**
- 표 셀로 살아남았고 사실이 온전하면 **생존**이다. 형태 변화는 손실이 아니다.
- "silently / no error" 절이 빠졌으면 나머지가 온전해도 **약화(weakened)**다.
- 조건절이 빠져 규칙이 일반화됐으면 **약화**다.
- 숫자에서 예외가 빠졌으면 **약화**다.

**심각도:**

| | 판정 | 조치 |
|---|---|---|
| `critical` | `mechanism`·`test`·`silent-failure` kind의 손실 또는 약화 | **그 파일을 되돌리고 재작업.** D39의 유일한 실패 조건 |
| `moderate` | `counter-case`·`number-with-exception` 손실 | 복원한 뒤 통과 |
| `minor` | `rationale` 손실 | 판단. 연역 가능한 rationale이면 의도된 삭제 |

### 2.3 실행 워크플로우

구현 세션은 파일당 이 워크플로우를 돌린다. 서브에이전트 모델은 `sonnet`. 파일당 에이전트 6개(추출2 + 압축1 + 블라인드1 + 판정1, 여유 1).

**스크립트 원형이 이 디렉토리에 있다: [`claim-ab-workflow.js`](claim-ab-workflow.js).** 계획 세션의 파일럿이 실제로 실행한 스크립트 그대로이므로, 문안(`EXTRACT_RULES`·`DISCRIMINANT`)이 §3의 결과를 낸 바로 그 문안이다.

구현 세션용으로 바꿀 것:

| 바꿀 것 | 이유 |
|---|---|
| `SRC`를 대상 파일 경로로 | — |
| 압축 에이전트를 2개 → 1개로 | 파일럿은 재현성 측정을 위해 2개였다. 재현성은 이미 확인됐다(§3) |
| `DISCRIMINANT`에 **T1b를 추가** | 파일럿 문안에는 없다. `02-compression.md` §2.1의 T1b 문단을 그대로 붙인다 |
| 판정 결과를 커밋 메시지에 붙일 형태로 반환 | 손실/약화 목록이 리뷰 근거다 |

> **`meta`는 pure literal이어야 한다** — 변수·함수 호출·스프레드·템플릿 보간 금지. 그리고 워크플로우 스크립트에서 `Date.now()`/`Math.random()`/무인자 `new Date()`는 throw한다.

## 3. 파일럿 결과 (계획 세션, 2026-08-03, `agents.md`)

가장 밀도가 높은 파일에 대해 8-에이전트 워크플로우를 실행했다. 측정 목적은 셋이었다.

### 3.1 재현성 — **통과**

독립 압축 에이전트 2개(sonnet)가 같은 판별식 문안으로:

| | 결과 | 표 행 | 헤딩 구조 | 가드레일 앵커 |
|---|---:|---:|---|---|
| A | 3,377 → **3,156** (−6.5%) | 37 | 원본과 동일 | 6/6 생존 |
| B | 3,377 → **3,180** (−5.8%) | 28 | 원본과 동일 | 6/6 생존 |

**0.7%p 안에서 일치했다.** 그리고 §2.1의 다섯 가지 스캐폴딩 형태를 둘 다 정확히 같은 곳에서 잡아냈다:

```
"Resist that."                          → 삭제 (설득)
"The temptation in a meta-skill..."     → 삭제 (설득)
"The practical implication:"            → 삭제 (메타 서술)
"Concretely, when the interview..."     → 삭제 (메타 서술)
"Three things in that body are..."      → 삭제 (메타 서술)
```

**판별식은 사람/에이전트가 바뀌어도 같은 결과를 낸다.** 이게 이 작업의 가장 큰 실패 모드(구현자마다 다른 기준)를 제거한다.

### 3.2 회수량 — **추정이 틀렸다**

초안은 10~16%를 예상했다. 실측은 **~6%**다. 원인은 명확하다:

> **패러프레이즈 금지가 표 변환을 재포맷으로 만든다.** 에이전트가 원문 문장을 통째로 셀에 옮기므로 절약되는 건 셀 사이 연결 산문뿐이다. `agents.md`의 `model` 문단은 표로 바뀌고도 212 → ~200단어였다.

이 발견으로 판별식에 **T1b(표로 옮긴 뒤 셀 안에서 T2 재실행, 셀 한정 패러프레이즈 허용)** 가 추가됐다. 근거는 행·열 레이블이 주장을 고정하므로 셀 안에서는 표류할 자리가 없다는 것. **T1b는 아직 미검증이다** — 구현 세션의 첫 파일(`agents.md`)이 이 파일럿 수치를 기준선 삼아 검증한다.

참조 구현: [`example-agents-compressed.md`](example-agents-compressed.md) — T1/T2가 실제로 어떻게 보이는지, 그리고 T1b가 겨냥하는 셀들이 어떤 모양인지.

### 3.3 검출력 — kind 분포가 후보 손실을 잡았다

추출 4회의 kind 분포:

| kind | orig-A | orig-B | blind-A | blind-B |
|---|---:|---:|---:|---:|
| `mechanism` | 37 | 38 | 37 | 51 |
| `decision-rule` | 34 | 40 | 33 | 34 |
| `test` | 4 | 4 | **6** | **5** |
| `counter-case` | 4 | 3 | **6** | 4 |
| **`silent-failure`** | **9** | **9** | **6** | **6** |
| `number-with-exception` | 1 | 0 | 1 | 0 |
| `rationale` | 18 | 18 | 25 | 28 |
| **합계** | **107** | **112** | **114** | **128** |

**두 가지가 읽힌다.**

**(1) 추출 프로토콜이 안정적이다.** 원본에 대한 독립 추출 2회가 107 vs 112(4.7% 차)이고, kind별로는 거의 일치한다 — `mechanism` 37/38, `silent-failure` 9/9, `test` 4/4. 즉 "무엇이 원자적 주장인가"에 대해 에이전트들이 같은 판단을 한다.

**(2) `silent-failure`만 떨어졌고, 독립 실행 2회가 같은 숫자를 냈다.** 9 → 6, 두 번 다. 다른 kind는 전부 유지되거나 올랐다(표 변환이 주장을 이산화하므로 총량이 오르는 건 정상이다). **오직 N4 범주만 하락했고 그건 우연으로 보기 어렵다.**

이게 실제 손실인지 재분류인지(같은 주장을 `mechanism`으로 태깅했을 수 있다 — blind-B의 `mechanism`이 51로 튀었다)는 판정 에이전트가 가른다. **하지만 어느 쪽이든 요점은 같다: 판정을 돌리기 전에, 개수만 세는 것으로 후보 손실이 지목됐다.** 그래서 §2.2에 kind 분포 비교를 판정 앞 단계로 넣었다.

### 3.4 남은 미검증 — 씨앗 손실 테스트

**kind 분포가 신호를 준다고 해서 판정 단계의 검출력이 검증된 건 아니다.** 판정이 손실 0을 보고하면 두 가지 중 하나다:

- (a) 압축이 정말 안전했다
- (b) **판정이 무력하다**

(b)를 배제하는 방법: 압축본에서 알려진 claim 하나(가급적 `silent-failure` 하나)를 의도적으로 지운 변형본을 만들어 판정을 한 번 더 돌린다. 그걸 못 잡으면 프로토콜을 고치고, 고치기 전에는 나머지 7개 파일을 시작하지 않는다. **검출력이 검증되지 않은 안전망은 헛된 안전감이고, 그게 앵커 grep만 믿었던 v2보다 나쁘다.**

### 3.5 부수 발견 — 에이전트의 자기 보고 단어 수를 믿지 말 것

압축 에이전트가 `compressedWords: 3093`을 보고했는데 `wc -w`로는 3,180이었다. **단어 수는 반드시 파일에서 직접 측정한다.**

## 4. L5 — 인터뷰 도그푸딩 (D40)

### 4.1 왜 필요한가

v2가 인터뷰를 네 곳 건드렸다.

| # | 변경 | 검증 상태 |
|---|---|---|
| I1 | 스코프 축 (`CLAUDE.md` vs `CLAUDE.local.md` vs auto memory) | 미검증 |
| I2 | 감산 게이트 ("만들지 않기로 한 것을 말하고 기록하라") | 미검증 |
| I3 | 인터페이스 프로브 + 권한 확대 별도 질문 | 미검증 |
| I4 | 배포 축 | 미검증 |

**넷 다 사람이 한 번도 끝까지 안 돌려봤다.** `AskUserQuestion`이 서브에이전트에 존재하지 않으므로(`agents.md:49`) 자동화가 원천적으로 불가능하다 — 그래서 v2가 L5를 미실행으로 남겼다.

### 4.2 시나리오

**대상: 하네스가 없는 작은 오픈소스 클론, `new` 모드.** `improve` 모드는 기존 spec이 있어 스코프 축·배포 축 질문이 당연해지므로 I1/I4를 제대로 시험하지 못한다.

```
1. 하네스가 없는 작은 레포를 클론 (언어/빌드 시스템이 명확한 것)
2. 새 Claude Code 세션에서 "이 프로젝트 하네스 만들어줘"
3. 인터뷰를 끝까지 진행 — 중간에 조종하지 않는다. 관찰이 목적이다
4. 생성까지 완료, validate_harness.py 통과 확인
5. 아래 체크리스트로 판정
```

### 4.3 판정 체크리스트

| # | 확인할 것 | 통과 조건 |
|---|---|---|
| L5-1 | Phase 0 감사가 실제로 먼저 돌았는가 | `audit_harness.py` 호출이 인터뷰보다 앞선다 |
| L5-2 | **I1 스코프 축** — "이건 당신만 필요한 건가, 팀 전체인가"를 물었는가 | 개인 사실이 나왔을 때 `CLAUDE.local.md`로 라우팅한다 |
| L5-3 | **I3 인터페이스 프로브** — 훅으로 라우팅하기 전에 인터페이스를 탐색했는가 | 최소 1회 시도. 해당 없으면 "해당 없음"이라고 말한다 |
| L5-4 | **I2 감산 게이트** — 만들지 않기로 한 것을 말하고 spec에 기록했는가 | Change history 또는 Design rationale에 남는다 |
| L5-5 | **I4 배포 축** | 물었거나, 코드베이스가 이미 답한다고 판단하고 그 판단을 말했다 |
| L5-6 | 발산/수렴 구분 | 목표·페인포인트는 대화로, 알려진 선택지는 `AskUserQuestion`으로 |
| L5-7 | 코드베이스가 답하는 걸 묻지 않았는가 | 빌드 명령·테스트 러너를 되묻지 않는다 |
| L5-8 | 보호 경로 경고 | 첫 `.claude/` 쓰기 전에 1회 경고한다 |
| L5-9 | spec 승인 게이트 | 생성 전에 승인을 받는다 |
| L5-10 | **압축 교리가 실제로 반영됐는가** | 생성된 CLAUDE.md·스킬의 문단이 짧고, why가 한 절로 붙어 있다 |

**L5-10이 v3 고유 항목이다.** 나머지는 v2의 미검증 부채이고, 이건 v3가 실제로 작동했는지의 유일한 e2e 증거다.

### 4.4 판정 처리

- L5-2/3/4/5 중 하나라도 실패 → **인터뷰 결함이다.** v3 범위 안에서 고친다(`interview.md`는 어차피 대상 파일).
- L5-10 실패 → **교리가 도달하지 못했다.** PR1을 재검토한다. 이 경우 v3의 핵심 주장이 반증된 것이므로 머지 전에 해결해야 한다.
- 나머지 실패 → 기록하고 심각도 판단.

결과는 이 문서 §5에 기록한다.
