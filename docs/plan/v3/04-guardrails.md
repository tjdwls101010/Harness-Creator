# R1 (v3) — 린트 짝이 있는 gotcha를 어디까지 자를 수 있나

> **이 문서가 R1의 정본이다.** 원본은 `docs/plan/v2/research/audit-synthesis.md` §4에 있고 **그대로 동결한다** — 그 문서 스스로 *"이 문서는 원본 그대로 보존한다 — 계획 문서가 여기서 결정을 추출했고, 인용된 라인 번호와 측정치의 출처가 여기다"*라고 쓴다. 인용 원장이지 살아 있는 스펙이 아니다.
>
> v2 원본에는 이 문서를 가리키는 한 줄만 추가했다.

## 1. 개정 문안

**R1 (v2, 원본):** "린트 체크가 남아 있는 산문 gotcha는 절대 자르지 않는다."

**R1 (v3):**

> **린트 체크가 있는 gotcha는 산문에서 *결정*을 남기고 *결과*를 체크 메시지로 옮긴다. 산문 전체를 지우지는 않는다.**
>
> 근거: 린트는 생성 *후*에 돌므로 작성 시점의 결정을 대신할 수 없다. 옮길 수 있는 건 "틀리면 무슨 일이 나는가"이고, 남겨야 하는 건 "그래서 무엇을 고르는가"다.
>
> **추가 제약 (v3 구현 세션):** 결과절은 **출처가 있을 때만** 옮긴다. 문서가 침묵하는 결과를 그럴듯하게 지어내면 그건 압축이 아니라 **없는 gotcha를 만드는 것**이고, 이 스킬의 가치 명제 자체를 무너뜨린다. PR1에서 계획이 지목한 6개 중 3개가 여기 걸려 산문도 체크 메시지도 그대로 뒀다.

## 3. 산문이 전부 남아야 하는 두 쌍

### 3.1 쌍 10 — pure-literal `meta` (원본이 이미 지목)

체크는 두 가지만 본다: `export const meta =` 뒤에 `{`가 오는가, 그 블록 안에 `name:` 토큰이 있는가. **값이 순수 리터럴인지는 절대 보지 않는다.** `export const meta = { name: computeName(), description: SOME_VAR }`는 두 정규식을 깨끗하게 통과한다.

즉 체크는 임의로 만족시킬 수 있고, 다른 어떤 함수도 순수성을 재검사하지 않는다. **체크를 통째로 지워도 산문은 전부 남아야 한다.**

### 3.2 쌍 9 — `@import` 백틱 억제 (v3에서 새로 발견)

**R1이 이 쌍을 양방향으로 분류한 것이 지금은 틀렸다.** B1 수정(`5f93e46`)이 `_AT_IMPORT_RE`를 `validate_harness.py`에서 `harness_common.py`로 옮기면서 백틱 억제를 `mask_code()`의 부산물로 바꿨다 — 코드 펜스와 인라인 코드 스팬을 통째로 가리는 함수이고, dead-link 검사와 generic-advice 검사도 같이 쓴다.

결과: **"백틱 밖의 `@`는 항상 확장된다"는 사실을 주장하는 finding이 존재하지 않는다.** 스크립트는 어느 쪽이든 올바르게 파싱할 뿐, 작성자가 억제를 *의도했는지*에 대해 아무 의견이 없다. 산문이 경고하는 실수 — 파일 존재를 언급하려다 실수로 내용을 통째로 import하는 것 — 은 린트가 잡지 못한다.

**그러므로 쌍 9도 쌍 10과 같은 취급을 받는다: 산문 전부 보존.** R1의 원래 분류를 믿고 여기서 결과절을 옮겼다면, 잡히지도 않는 실수의 유일한 경고를 지웠을 것이다.

## 4. PR2에 대한 결론

R1(v3)은 **PR2에서 산문 삭제를 하나도 승인하지 않는다.** 여덟 쌍은 이미 분해돼 있고, 두 쌍은 산문이 전부 남아야 한다.

이건 실패가 아니라 정보다. D33의 가설은 "린트 짝이 있는 산문에 옮길 수 있는 결과절이 남아 있다"였고, **실측하니 v2가 이미 다 옮겨 놨다.** R1은 v3에서 압축 예산의 원천이 아니라 **do-not-cut 목록**으로 기능한다. PR2의 회수는 전적으로 T1b와 T2(스캐폴딩 삭제)에서 나와야 한다.

## 5. R2와 R3

**R2 (`once: true` 3중 기술) — 무변경.** 근거가 그대로다: `SKILL.md`가 컴포넌트 타입마다 별도 reference 로드를 강제하므로 에이전트를 생성하는 모델은 `skills.md`를 열지 않는다. 의도된 중복이다. `agents.md`의 Explore/Plan gotcha가 `hooks-events.md`·`skills.md`·`e2e-testing.md`에 재기술된 것도 같다.

**R3 (30행 라우터) — 좌표 정정.** 원문은 `hooks.md:118-153`이라 쓰는데 **현재 라우터는 `:154-189`다** (헤딩 `## The router: which event for which job`이 `:154`, 30개 이벤트 행이 `:158-189`). `:118-153`은 workspace trust 게이팅, 보호 경로, auto 모드의 broad-allow 정지, 복합 명령 매칭이다.

**두 구간 다 보호 대상이지만 사유가 다르고, 이걸 섞으면 사고가 난다.** R3만 기억한 채 `:118-153`을 지키고 `:154-189`를 자르면 정확히 R3가 막으려던 일이 일어난다 — staged split이 라우팅 실패가 되고, 모델이 이벤트 하나 고르려고 `hooks-events.md` 3,777단어를 통째로 로드한다. `:118-153`의 보호 근거는 N4(조용한 실패)와 N5(명명된 메커니즘)다.

R3가 같이 지목한 `e2e-testing.md`의 두 표(assertion-type, feedback-routing)도 유지한다.

## 6. R1의 좌표는 다시 낡는다

이 표의 행 번호도 다음 개정에서 어긋난다. **개념으로 재탐색하는 것이 정본 절차이고, 행 번호는 편의다.** `tests/test_skill_surface.py`의 `GuardrailTests`가 토큰 앵커로 삭제를 막고 있으므로 실제 안전망은 그쪽이지 이 표가 아니다 — 다만 앵커는 *삭제*만 잡고 *희석*은 못 잡으므로(v2에서 손실 4건) claim A/B가 필요하다.
